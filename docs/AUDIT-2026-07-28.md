# Audit findings — 2026-07-28

Multi-agent audit of the codebase, the live `state.db`, and `docs/EXPANSION-PLAN.md`.
Method: 20 agents — architecture mapping, strategy validation, eight audit
dimensions each followed by an adversarial verifier, then gap analysis. No code was
modified and no StockX API call was made by the auditors; all database access was
`file:state.db?mode=ro`.

**Data caveat that applies to every empirical claim below:** the dataset spans
roughly 29 hours (2026-07-27T05:29 → 2026-07-28T12:00) with 17 scanner restarts,
and per-retailer exposure is very unequal (teamsport 88 scans vs sportland_lv 1).
Treat distributions as indicative, not seasonal.

Two dimensions — reliability and maintainability — failed on connection errors and
were re-run separately; see [Pending](#pending) at the end.

## 0. The three findings that invalidate current output

These were re-verified by hand against `state.db` after the audit returned. All
three are confirmed, not inferred.

### 0.1 Alerts name the size with the best price, not the size in stock
**`arb/retailers/sportland.py:145-147`** — CRITICAL

```python
enriched.sizes = [RetailSize(label=lbl, system="EU", in_stock=parent_in_stock)
                  for lbl in sorted(set(labels))]
```

Every size label inherits the *parent product's* stock flag. Consequently
`arb/scanner.py:224` (`if not size.in_stock: continue`) never filters a Sportland
size, and `arb/scanner.py:272` picks `max(..., key=score)` — systematically the
extreme size that carries the highest price precisely because nobody stocks it.

Verified across all 7 alerts ever produced: the stored `sizes[]` marks **every**
row `in_stock: true`, while the alert text simultaneously says *"1/11 sizes in
stock"*. Five of seven named a size with roughly a **9% prior probability of
existing**. Alerted sizes: 40.5, 42, 45.5, 45.5, 45.5, 46, 46.

All 7 alerts the system has ever sent came through this one path
(`size_stock_unverified`, `arb/scanner.py:268-275`).

**Fix:** do not synthesise per-size stock. Either mark the product
`size_stock_unverified` *and* refuse to name a specific size in the alert, or
derive real per-size availability. Until then the alert is naming a coin flip.
**Effort: S**

### 0.2 Size selection and ranking use the ask, not the gated bid
**`arb/profit.py:89-98`** (`opportunity_score`) — CRITICAL

`opportunity_score` ranks on `best_profit = max(sell_now, list_ask)`. Verified
numerically: **all 7 stored scores equal exactly `2 × list_ask.profit`.**

| Shoe | score | sell_now | list_ask |
|---|---|---|---|
| Nike C1TY Premium | 310.02 | **13.26** | 155.01 |
| Lunar Force 1 Duckboot | 331.77 | 59.14 | 165.88 |
| Killshot 2 | 158.52 | **10.13** | 79.26 |

Because the size-unverified collapse at `arb/scanner.py:272` selects by `score`,
the *size chosen* is the one with the best **ask** — a price you cannot take today
— and the sell-now figure is then reported beside it. The gate is bid-only
(`require_live_bid: true`), but the selection is not.

**Fix:** score on `_gate_profit` (the same number the filter uses), not on
`best_profit`. **Effort: S**

### 0.3 Half the API budget is spent on products that can never alert
**`arb/scanner.py:311-313`** — CRITICAL

`_market_ttl_minutes` maps `best_profit IS NULL` to `refresh_minutes_hot`
(45 min) on the reasoning "never assessed → look now". But NULL also means
"assessed, and there was no bid on any variant".

Live measurement: **1,577 of 3,089 `sku_watch` rows are NULL (51%), and 100% of
them have no `highest_bid` on any cached variant** — so under
`require_live_bid: true` they can never produce an alert. They are nonetheless
refreshed 32×/day.

```
implied demand from NULL rows alone : 50,464 calls/day
daily_request_budget                : 23,500
```

Consequences already in the logs: 207 × `stopping scan early: daily StockX
request budget reached`; a **13-hour daily blackout** (zero `market_history` rows
2026-07-27T16:00 → 07-28T05:00) during which 187 scans discarded **251,631
candidates** unexamined.

**Fix:** distinguish "never assessed" (NULL, no `checked_at`) from "assessed, no
bid" (cold). One-line change; frees roughly 46,000 calls/day — more headroom than
all four expansion phases would consume. **Effort: S**

## 1. StockX API — terms and throttling risk

### 1.1 The 1 req/s limit is per-process and has already been breached
**`arb/stockx/client.py:60,66-71,83`** — CRITICAL (ToS risk)

`self._lock = asyncio.Lock()` and `self._last_request_at` are *instance* state;
nothing coordinates across processes. Evidence from `api_requests` timestamps:

```
14:40:45.634862  d=0.431
14:40:46.264904  d=0.630
14:40:46.699962  d=0.435
14:40:47.313666  d=0.614   ← two streams, each pacing 1.05 s, offset ~0.44 s
```

Sustained ≈1.9 req/s against a documented 1 req/s hard limit
(`README.md:115-116`, `config.yaml:55`). **Known cause: running `arb report` or
`arb resolve` while the 24/7 scanner is live** — each builds its own client.

**Fix:** move the rate limit out of the process — a lease row in `state.db`
stamped inside the existing lock, or a file lock. Interim: refuse to run
`report`/`resolve` while a scan is in flight (the `kv` scan markers already make
this detectable). **Effort: M**

### 1.2 `arb report` bypasses the budget entirely
**`arb/cli.py:254-256`** — HIGH

`report` constructs `StockXClient` against `Database(":memory:")`, so
`api_requests_last_24h()` always returns 0, the budget is never enforced, and its
requests never land in the counter. It also forces a fresh `/oauth/token` POST
every invocation (empty `kv`), and `--limit` truncates *printing*, not the fetch
loop (`cli.py:259` iterates the whole `opportunities` table).

**Fix:** pass the real `Database`; move `--limit` before the fetch loop.
**Effort: S**

### 1.3 `Retry-After` is honoured only when all-digits
**`arb/stockx/client.py:110-112`** — HIGH

```python
delay = float(retry_after) if retry_after and retry_after.isdigit() \
    else backoff * (1 + random.random() * 0.25)
```

RFC 9110 permits an HTTP-date form, which `.isdigit()` rejects — falling back to
~2 s. Log evidence: 5 × 429, and the entire logged delay distribution is
2.0–2.5 s. Retrying a 429 after 2 s when the server asked for 60 s is a standard
key-suspension trigger.

**Fix:** parse both forms (`float`, then `email.utils.parsedate_to_datetime`),
clamp to a maximum, treat the value as a floor. **Effort: S**

### 1.4 Token refresh has no mutex and is unbudgeted
**`arb/stockx/auth.py:46-53`, called at `arb/stockx/client.py:80` (outside the lock)** — HIGH

8 retailer loops run concurrently (`arb/scanner.py:474`); on expiry all 8 can fail
the cache check in the same tick and POST simultaneously. These POSTs are neither
throttled nor counted. Currently masked — the ~11 h token means the window opens
about twice a day.

**Fix:** `asyncio.Lock` on `TokenManager` with double-checked cache read; count
token POSTs against the budget. **Effort: S**

### 1.5 Refresh-token rotation is discarded
**`arb/stockx/auth.py:71-74`** — HIGH

Only `access_token` is read from the refresh response. If StockX rotates refresh
tokens, the next expiry produces a permanent, silent outage: `AuthError`
subclasses `RuntimeError`, so it escapes the handlers at `arb/scanner.py:86-98`
into `run_loop`'s blanket `except Exception`, and every retailer retries a doomed
POST once per interval forever.

**Fix:** persist a rotated `refresh_token` via the existing
`authorize.save_refresh_token`; catch `AuthError` explicitly with long backoff.
**Effort: S**

## 2. Arbitrage maths — where profit is overstated

The formula itself is sound: `arb/profit.py:30-45` nets transaction + processing
fees, outbound shipping and the VAT wedge, counts shipping exactly once, and
reproduces all 7 stored alerts to the cent. VAT isolation is genuine and is a
clean no-op today. **The overstatement is in what the formula is never told.**

Ranked by euros on a typical €100 buy:

| # | Gap | Where | Effort |
|---|---|---|---|
| 2.1 | **LT revenue split entirely unmodelled** — source of 4 of 7 alerts. `config.yaml:165-170` asserts in prose "Profit figures for this source are correct as printed"; `RetailerConfig` (`arb/config.py:111-144`) has no share field | config | S |
| 2.2 | **Inbound retail delivery is €0 for 7 of 8 retailers** — and `pickup_available`, the field that would justify it, is dead (see §4) | `arb/config.py:118` | S |
| 2.3 | **No failed-authentication / return / non-delivery term anywhere** | `arb/profit.py` | S |
| 2.4 | **Teamsport's 10% applied unconditionally**, stacking on already-marked-down prices — unlike `sale_discount_pct`, which is correctly gated on `on_sale` | `config.yaml`, `arb/models.py:62-65` | S |

Together these plausibly consume the entire €10 floor on a €100 item.

**2.5 — `list_ask` is printed with no time-to-clear counterweight.** `undercut_eur:
0.00` means joining the back of the ask queue, and `est_days_to_clear` is
structurally always `None` (the official API supplies no sales velocity). Recorded
example: a €37.49 shoe alerted "sell now +€13.26" beside "list @ ask +€155.01
(+414%)". Consider suppressing `list_ask` from alerts, or labelling it as
unbounded-wait. **Effort: S**

**2.6 — ROIC is computed and never displayed; `est_days_to_clear` is always None.**
No capital-velocity signal exists. **Effort: S**

**2.7 — FX is a silent drop, not a conversion.** `arb/scanner.py:120` requires
`p.currency == "EUR"` with no log line, counter or review row; the check is not
re-applied after `enrich()` can rewrite currency. A PLN/SEK/GBP storefront would
be fully scraped, fully stored, and silently produce nothing — which reads as
"this retailer has no deals". **This is the highest-value non-category work for
multi-country expansion.** **Effort: M**

## 9. Reliability and alerting

### 9.1 A failed Discord send permanently suppresses the alert
**`arb/notify.py:135-137` + `arb/scanner.py:450-451`** — CRITICAL

The call order in `_maybe_alert` is correct — send, then record:

```python
scanner.py:450   await notifier.send(format_opportunity(opp, reason, cfg))
scanner.py:451   db.record_alert(opp.key, _gate_profit(...), ...)
```

But `DiscordNotifier.send` never signals failure:

```python
notify.py:135        if resp.status_code not in (200, 204):
notify.py:136            log.error("Discord send failed: %s %s", ...)
```

It logs and returns normally. On **any** non-2xx — 429 rate limit, 5xx, deleted
webhook (404), oversized payload — `send()` returns success-shaped,
`record_alert` fires, and `should_alert` (`db.py:256-268`) returns
`(False, "duplicate")` for that key **forever** unless profit moves ≥ €10.
`TelegramNotifier.send` (`notify.py:162-164`) has the identical defect.

Not theoretical: Discord webhooks rate-limit at ~5 req/2 s; `max_per_scan: 20`
sends fire back-to-back with no delay (`scanner.py:101-103`) across 7 concurrent
retailer loops. On a 429 for chunk 1, `notify.py:129` immediately posts chunk 2.

Ironically, a notifier that *raises* is the safe failure — the exception kills the
scan before `record_alert`, so the alert survives to the next cycle.

**Fix:** have `send()` return `bool` or raise; only call `record_alert` on
success; add retries honouring Discord's `retry_after`. **Effort: S — three lines.**
**If only one thing on this list gets fixed, make it this one.**

### 9.2 No monitoring of the bot itself
**CRITICAL** — there is exactly one `notifier.send` call site in the codebase
(`scanner.py:450`). No heartbeat, no error notification, no budget-exhaustion
notice, no log rotation. Three specific blind spots:

- **The dashboard's error panel reads the wrong file.** Logging goes to stdout
  (`cli.py:36`) → `scanner.log`, but `dashboard.py:59-60` tails
  `scanner.err.log`, which contains only the `.bat` restart lines. Despite **17
  scanner restarts** recorded, the panel has shown zero errors; the one real
  traceback sits at `scanner.log:2023`, a file the panel never reads.
- **A retailer stuck "scanning" is exempt from the overdue check.**
  `dashboard.py:160` gates `overdue` on `not scanning`, and `scan_finished` is
  only written in the `finally` (`scanner.py:109`) — so a process killed mid-scan
  leaves `started > finished` permanently.
- **Liveness is inferred from log mtime** (`dashboard.py:53-56`). A scanner
  failing *every* scan still writes lines, so it reads UP.

**Fix:** daily digest + push on N consecutive failures, budget exhaustion, and
host give-up; point the error panel at `scanner.log`; add `RotatingFileHandler`
(`scanner.log` is already 3 MB after two days). **Effort: M**

### 9.3 The restock re-alert path is dead for the only retailers that alert
**`arb/scanner.py:424-435`** — HIGH

`db.mark_out_of_stock` has one call site, inside a block guarded by
`if not opp.retail.price_verified`. But `_evaluate_product` already enriched the
product, and `sportland.py:152` sets `price_verified = True` — so the block is
skipped and the function is never reached. Confirmed: **all 7 opportunity rows
have `was_in_stock=1`; zero rows have 0.** A shoe that sells out and returns at
the same price can never re-alert. **Effort: S**

### 10.1 `2XL` matches `2XS` at full confidence — a bug in today's own size fix
**`arb/matching.py:131` (`_sizes_equal`)** — CRITICAL, **verified by hand**

```
_num('2XL')=2.0  _num('2XS')=2.0  _sizes_equal=True  confidence=1.0
```

The numeric branch runs first and `re.search(r"\d+")` grabs the leading digit of
`2XL`, so `_letter()` is never consulted. This directly contradicts the
function's own docstring (`matching.py:126-129`): *"treating that as a match
would sell an S into an XL bid."* `L`/`M` and `XL`/`XXL` are correctly rejected —
only the numeric-prefixed apparel sizes leak.

label as `us_size`, which `reede.py:139-145` does when
`default_size_type == "US"`. `config.yaml:102-104` points reede at `/mehed` and
`/naised`, so apparel is in scope.

**Fix:** try `_letter()` before `_num()`, or exclude `_APPAREL_SIZE` matches from
the numeric branch. **Effort: S**
